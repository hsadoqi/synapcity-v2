# @synapcity/server-supabase

Owns: the server-side Supabase adapter. It builds request-bound clients from host-supplied cookies and implements the identity boundary's `IdentityProvider` port for Supabase Auth. It is the only server package that imports `@supabase/*` (workspace conventions, vendor adapters). M7.2 added the provider auth operations (registration, recovery, email change and resend, own password reset, account linking and unlinking) and the provider-user translation used by profile operations. The Supabase review fixes (2026-10-27) added the session operations, the shared failure helper and the generated database types. Session refresh deliberately remains in the web host because the portable extraction was too small to justify an unverified `server-only` import from the proxy.

Runtime: server only. The root entry starts with `import 'server-only'`. Category rules: [server README](../README.md) and [ADR-0014](../../../docs/architecture/decisions/0014-multi-app-package-boundaries.md); auth rules: [ADR-0006](../../../docs/architecture/decisions/0006-authentication-with-supabase.md).

## Public interface

`@synapcity/server-supabase` (root entry):

| Export                                                                                                                                                                                                                                       | Meaning                                                                                                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `createRequestClient(options)`                                                                                                                                                                                                               | `{ url, publishableKey, cookies }` to a Supabase client for one request. `cookies` is the host's `{ getAll, set }`; a failed write during a Server Component render is ignored                                                                                                      |
| `registerWithPassword`, `requestRecoveryEmail`, `resendSignupConfirmation`, `updateOwnPassword`, `changeEmail`, `resendEmailChange`, `sendOwnPasswordReset`, `startAccountLink`, `disconnectAccount` (and their `*Input` / `*Outcome` types) | Provider auth operations. Each takes the request-bound client as its first argument and returns a plain scalar outcome (never an SDK user, session, token or error). They read no environment, cookies or fixture mode, call no `next/*` API and do not log                         |
| `signInWithPassword`, `startOAuthSignIn`, `exchangeAuthCode`, `signOutSession` (and `SignOutScope`, their `*Outcome` types)                                                                                                                  | Session operations, same contract. `exchangeAuthCode` returns the user id and whether a new account still needs its profile step, never the SDK user. `signOutSession` takes a scope (the web host signs out `local`) and never throws                                              |
| `toProviderFailure(error)`, `ProviderFailure`                                                                                                                                                                                                | Any Supabase error (Auth, PostgREST or Storage) reduced to `{ code?, status? }`, with absent keys left out. The one conversion every package uses before a failure leaves it                                                                                                        |
| `Database`, `Json`, `Tables`, `TablesInsert`, `TablesUpdate`                                                                                                                                                                                 | Types generated from the schema (`src/database-types/database.types.ts`). `createRequestClient` is typed with `Database`, so queries and rows are checked against it                                                                                                                |

| `supabaseIdentityProvider(client)`                                                                                                                                                                                                           | `IdentityProvider` over `getClaims()` and `getUser()`: a retryable fetch error is `unreachable`, any other error `refused`, even when a user came back with it                                                                                                                      |

## Rules

- Build a client per request and never store it in a module variable (ADR-0008).
- The package never reads cookies, headers or environment variables itself; the host supplies them (ADR-0014 section 3).
- `src/database-types/database.types.ts` is generated from the migrations: never edit it by hand. After a migration, start a database the migrations were applied to (`pnpm exec supabase db start`, then `pnpm exec supabase migration up --local`; or any Postgres via `SUPABASE_DB_URL`) and run `pnpm db:types`. The script (`scripts/db-types.mjs`) runs the pinned Supabase CLI and formats the result with the repository's Prettier, so the output depends only on the migrations and those two pinned tools. The CI `db-types` job regenerates it on a fresh database and fails on any difference. That checks the types against the migrations, not against the hosted project, and needs no credentials. Knip skips only the file's unused-export checks (`Constants`, `Enums` and `CompositeTypes` are generator boilerplate).
- The file has no `__InternalSupabase.PostgrestVersion`. That value describes the PostgREST the schema is served by (the hosted project reported `14.18` on 2026-10-27; the CLI's local stack runs 16.5), not the schema, so a schema-derived file cannot carry it. In `@supabase/postgrest-js` 2.117.3 it only unlocks `maxAffected()`, which nothing here calls. If that is ever needed, pass the version as a client option in `createRequestClient`. _Superseded (2026-10-27): the file was first generated from the hosted project (`gen types --project-id`), which no CI job could reproduce without credentials._
- Internal: `auth-errors` (`classifyAuthError`, the signed-out, unavailable or provider-error mapping the account operations share).
- `@supabase/ssr` and `@supabase/supabase-js` are pinned to the same exact versions as `apps/web`, which still imports them directly until its remaining Supabase code migrates.
