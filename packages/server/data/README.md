# @synapcity/server-data

Owns: the Space, document and dashboard queries and writes against a Supabase request client the host supplies (ADR-0012, ADR-0013). Reads the owner's Spaces, documents and dashboards, and the documents and dashboards that take part in one Space; creates all three from a name, and writes pinned on all three and last viewed on Spaces. The document and dashboard reads and the pin write moved here from `apps/web/src/lib/owned-records` before Milestone 8 (owner decision, 2026-10-27), which builds on `records/`.

Runtime: server only. The root file starts with `import 'server-only'`, and no other file in the package imports it. Dependencies: `@synapcity/domain-records` for the base record contract and `@synapcity/domain-spaces` for the Space contract, `@synapcity/server-supabase` for the typed client and `toProviderFailure`. UUID checks for the concrete Supabase tables stay in this adapter rather than changing the base contract's opaque id. Category rules: [server README](../README.md) and [ADR-0014](../../../docs/architecture/decisions/0014-multi-app-package-boundaries.md).

## Rules

- Row-level security scopes every query. No owner id is passed to any function.
- The package never logs and never reads `NODE_ENV`, fixture mode or any other environment. Hosts log by code and status only and decide when fixtures apply.
- A participation row whose item the caller cannot see is skipped, not an error.
- Per-Space `pinned` and `position` on the participation rows are read only by `listSpacesWithRelations` and `getSpaceRelations`; the item reads (`listSpaceDocuments`, `listSpaceDashboards`) do not read them yet.
- Row types and row mapping are private to the package (`owned-row`, shared by the three tables). Rows are typed from the generated `Database`; each query is a literal select, one per kind, so the generated types check it.
- Reads a page needs throw, so the route's error page handles them. The thrown message names the read and the error code only (`Failed to load spaces (code 42501)`), never the database's message. Writes return outcomes and never throw for a database error.

## Scripts

`lint`, `check-types`, `test`, `test:coverage`. Tests sit beside the units (`*.test.ts`) and run against a stub client; they do not reach a database. `test:db` runs the `*.dbtest.ts` files against the worktree's disposable stack (`pnpm db:stack start`), among them `records/latest-order.dbtest.ts`, the ordering-parity test of the bounded reads; `test:db:budgets` runs the history budgets.
