# @synapcity/frontend-preferences

Owns: the browser half of preferences (ADR-0010, ADR-0003), including the one runtime owner of a person's preferences in the browser (`PreferencesProvider`). It reads the saved preferences in the browser and applies them to the page: the boot scripts and apply functions, font loading, the device store, the consent and system-signal hooks, mode (`ModeProvider`, `useMode`, moved from `frontend-ui` in M6.2), and the shared look cookie (M6.3). `frontend-ui`'s `ModeToggle` imports `useMode` from here. Plans: [M6.2](../../../docs/superpowers/plans/2026-10-24-m6-2-frontend-preferences.md), [M6.3](../../../docs/superpowers/plans/2026-10-24-m6-3-shared-look.md).

Runtime: browser and React, framework-neutral. It imports no `next` and no server code. Dependencies: `@synapcity/domain-preferences` for the preference shapes, catalogs and rules, and `react` for types. It never depends on `@synapcity/frontend-ui`; `frontend-ui` depends on it for `ModeToggle`. Category rules: [frontend README](../README.md) and [ADR-0014](../../../docs/architecture/decisions/0014-multi-app-package-boundaries.md).

## The preferences runtime

`PreferencesProvider` is the single owner of the preferences in effect. The host's server layout passes the `PreferencesSession` (guest, or an account with the row it read, `stored: null` when that read failed), the request's validated look, and the server action that saves the account part. It must sit inside `ModeProvider`, which owns colour mode; the runtime follows it and changes it through it.

- **Initialization and hydration.** The server render and hydration use only what the server knew (the look cookie, then the account), so server and browser render the same text. In a layout effect, before the first paint after hydration, the runtime reads the cached document, its ownership marker and the set-aside device display once, resolves the session with `resolveSession` from the domain package, and applies the result to `<html>`. When the document is absent, unreadable or blocked, the shared look cookie as it is then (else the request's look) supplies the device's visual fields; it is never adopted as a document.
- **Account-aware cache.** `synapcity-preferences` keeps its legacy bytes and shape (the boot scripts read it). Beside it, `synapcity-preferences-owner` records whose choices it holds. A legacy (unmarked) document keeps its bytes until the visitor makes a choice and is never adopted, and its consent is not honoured, because its owner is unknowable; a document of another account is never shown to or saved for this one; only a guest document that did not start from a legacy one is adopted at first sign-in.
- **Account lifecycle.** A new request-bound host value installs its `session` and save action atomically, so an in-place sign-in can adopt eligible guest choices and report this device's zone. Sign-in, sign-out and account switching re-resolve without remounting, and outcomes of saves made for the previous person are ignored. If a newest account change is queued behind an active save when the session changes, its captured payload is sent after that active request; it never enters the next session's runtime. A refreshed row for the same person is applied unless a save is pending, which supersedes it.
- **Persistence.** Every accepted change is written to the document, its marker, the look cookie and the set-aside display. Account saves are serialized: one in flight and only the newest waiting, so an older write never lands after a newer one; only the newest outcome is reported, and "Saved" is withheld while an account write is pending. A retryable failure is retried when the browser comes back online or on `retryAccountSave`; an ended session is not retried.
- **Other tabs.** A `storage` event is taken up only when the document belongs to the same person. The set-aside display is read with it so the "all devices" switch and active override converge too.
- **Status and consent.** Account failure is durable synchronization state (`accountFailure`, with the server's wording in `accountFailureMessage`), separate from transient local-save messages. `PreferencesStatus` reports what happened and the Settings feature words it. An unmarked legacy document is preserved but its consent is treated as not granted because its owner is unknowable.

Consumers read through selectors: `usePreferences(select)` and the category hooks `useRegionalPreferences`, `useThemePreferences`, `useAppearancePreferences`, `useNotificationPreferences`, `usePrivacyPreferences`. Unchanged sections keep their identity, so a subscriber to one category does not re-render when another changes. `useDateTimeFormatting` (every date and time in the interface), `useNumberFormat` and `useCanCollect` derive from them. Outside a provider these read fixed defaults, and `useCanCollect` is always false; `StaticPreferences` gives previews, stories and tests fixed values. `usePreferenceActions` returns `update`, `setDisplayOnAllDevices` and `retryAccountSave`.

The device store (`readStoredPreferences`, `writeStoredPreferences`, `clearStoredPreferences`, `readCacheOwner`, `writeCacheOwner`, `readDeviceDisplay`, `writeDeviceDisplay`, `deviceTimezone`) is the one place preferences are read from or written to browser storage. Each function behaves like the `localStorage` call it replaces, including throwing where `localStorage` throws, so the runtime can report failures consistently. Only the runtime calls it at run time. The other hooks are `useGlobalPrivacyControl` and `usePrefersDark`.

The shared look (M6.3): `readLookCookie`, `writeLookCookie` and `configureLookCookie` (the host sets the parent domain once; anything but a valid plain DNS host name is ignored), `saveLook`, `migrateLookToCookie`, `currentLook` and `shareMode`. The portable domain package owns serialization and server/header parsing. `lookHtmlAttributes` maps an already validated look to the safe `<html>` attributes and CSS variables that web and docs render on the server. Boot scripts prefer that server-resolved look, then a valid cookie, then the local-storage migration fallback; `modeBootScript` resolves `system` and seeds `next-themes`. `ModeProvider` writes the cookie only when given `shareLook`, so Storybook never does.

The compact cookie expression is generated from the same version, enum catalogs, text-size range and size cap as the domain `lookSchema`. Boot, React and server readers therefore reject a cookie as one whole unit when any field is missing or invalid. The expression is embedded in each standalone boot script, but has one source and an exhaustive parity test; the repeated generated text cannot drift independently.

The four boot scripts are inlined in the document head before first paint so saved preferences apply with no flash. Their three appearance/font/shape strings are pinned by `src/scripts/boot-scripts.expected.json`: change one only on purpose, then regenerate with `UPDATE_BOOT_SCRIPTS=1 pnpm --filter @synapcity/frontend-preferences exec vitest run src/scripts/boot-scripts.test.ts` and verify by running the same command without the environment variable.

## Rules

- One folder per unit under `src/scripts/`, `src/store/`, `src/hooks/`, `src/providers/`, `src/runtime/`, `src/utils/` and `src/types/`, each with its `index.ts`; imports between folders go through the folder's `index.ts`.
- No `next`, no server code, no `@synapcity/frontend-ui`, in production code, tests or stories.
- Outside this package, nothing reads or writes the preference keys directly, and nothing but `PreferencesProvider` owns preference state; read through its hooks.
- Stored keys, the `synapcity-preferences-saved` event name and the data attributes are contracts with the saved data and the CSS. Do not rename them here.
