# @synapcity/frontend-preferences

Owns: the browser half of preferences (ADR-0010, ADR-0003). It reads the saved preferences in the browser and applies them to the page: the boot scripts and apply functions, font loading, the device store, the consent and system-signal hooks, mode (`ModeProvider`, `useMode`, moved from `frontend-ui` in M6.2), and the shared look cookie (M6.3). `frontend-ui`'s `ModeToggle` imports `useMode` from here. Plans: [M6.2](../../../docs/superpowers/plans/2026-10-24-m6-2-frontend-preferences.md), [M6.3](../../../docs/superpowers/plans/2026-10-24-m6-3-shared-look.md).

Runtime: browser and React, framework-neutral. It imports no `next` and no server code. Dependencies: `@synapcity/domain-preferences` for the preference shapes, catalogs and rules, and `react` for types. It never depends on `@synapcity/frontend-ui`; `frontend-ui` depends on it for `ModeToggle`. Category rules: [frontend README](../README.md) and [ADR-0014](../../../docs/architecture/decisions/0014-multi-app-package-boundaries.md).

## Public interface

| Entry                             | Exports                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `@synapcity/frontend-preferences` | `PREFERENCES_STORAGE_KEY`, `PREFERENCES_SAVED_EVENT`, `applyAppearance`, `appearanceBootScript`, `applyThemeShape`, `previewShapeAttributes`, `previewTextScaleStyle`, `themeShapeBootScript`, `loadFont`, `applyFontPreferences`, `previewFontValue`, `previewFontStyle`, `fontBootScript`, `fontStylesheetUrl`, `fontStack`, `fontPreferenceVariables`, `lookHtmlAttributes`, `ModeProvider`, `useMode`, `RegionalProvider`, `useDateTimeFormatting`, `Mode`, `ResolvedMode`, `isMode`, `isResolvedMode`, `resolveMode`, `resolveSystemMode`, plus the store and hooks below |

The device store (`readStoredPreferences`, `tryReadStoredPreferences`, `writeStoredPreferences`, `clearStoredPreferences`, `announcePreferencesSaved`, `onStoredPreferencesChange`, `readDeviceDisplay`, `writeDeviceDisplay`, `deviceTimezone`) is the one place preferences are read from or written to browser storage. Each function behaves like the `localStorage` call it replaces, including throwing where `localStorage` throws, so callers keep their own `try`/`catch`. `useDateTimeFormatting` is how every date and time in the interface gets written: it resolves the saved regional settings (language, zone, hour cycle, date order, week start) through `resolveDateTimeFormatting` in the domain package, follows saves in this tab and others like `useCanCollect`, and needs no provider in the browser. `RegionalProvider` only gives it the server's view (the account's settings and last device zone) for the server render and hydration. The hooks are `useCanCollect` (consent for a collector, following other tabs and this tab's saves), `useGlobalPrivacyControl` and `usePrefersDark`.

The shared look (M6.3): `readLookCookie`, `writeLookCookie` and `configureLookCookie` (the host sets the parent domain once; anything but a valid plain DNS host name is ignored), `saveLook`, `migrateLookToCookie`, `currentLook` and `shareMode`. The portable domain package owns serialization and server/header parsing. `lookHtmlAttributes` maps an already validated look to the safe `<html>` attributes and CSS variables that web and docs render on the server. Boot scripts prefer that server-resolved look, then a valid cookie, then the local-storage migration fallback; `modeBootScript` resolves `system` and seeds `next-themes`. `ModeProvider` writes the cookie only when given `shareLook`, so Storybook never does.

The compact cookie expression is generated from the same version, enum catalogs, text-size range and size cap as the domain `lookSchema`. Boot, React and server readers therefore reject a cookie as one whole unit when any field is missing or invalid. The expression is embedded in each standalone boot script, but has one source and an exhaustive parity test; the repeated generated text cannot drift independently.

The four boot scripts are inlined in the document head before first paint so saved preferences apply with no flash. Their three appearance/font/shape strings are pinned by `src/scripts/boot-scripts.expected.json`: change one only on purpose, then regenerate with `UPDATE_BOOT_SCRIPTS=1 pnpm --filter @synapcity/frontend-preferences exec vitest run src/scripts/boot-scripts.test.ts` and verify by running the same command without the environment variable.

## Rules

- One folder per unit under `src/scripts/`, `src/store/`, `src/hooks/`, `src/providers/`, `src/utils/` and `src/types/`, each with its `index.ts`; imports between folders go through the folder's `index.ts`.
- No `next`, no server code, no `@synapcity/frontend-ui`, in production code, tests or stories.
- Outside this package, nothing reads or writes the preference keys directly; go through the store.
- Stored keys, the `synapcity-preferences-saved` event name and the data attributes are contracts with the saved data and the CSS. Do not rename them here.
