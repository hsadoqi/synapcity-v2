# @synapcity/domain-identity

Owns: portable identity contracts. The verified-identity result that server code receives from the identity boundary (Milestone 4); the name, avatar and profile schemas; the credential schemas (sign-in, registration, sign-up, new password, email request, update password) with their refusal helpers; and the pure display-user rules (name check, initials, the display-name resolution, avatar URL, profile setup). An earlier note planned the credential schemas for a separate `domain-auth` package; whether they should move there is an open owner question recorded in the M7.1 plan.

Reading Supabase data shapes is not identity's job: the claims mapping (`profileFromClaims`, `currentUserFromClaims`), the provider-image reader (`providerImageFrom`) and the Supabase rate-limit codes (`isRateLimited`) moved to `@synapcity/server-supabase` on 2026-11-11, because only server code reads them. `isUploadedAvatar` still reads the storage path in the browser until the avatar form gets a server-derived removability flag (deferred to the avatar and profile UI task), and the profile-setup flag in `user_metadata` stays until the profile-completion task settles how completing and skipping the step are stored.

Runtime: portable TypeScript. The only runtime dependency is `zod`, for the schemas. Category rules: [domain README](../README.md) and [ADR-0014](../../../docs/architecture/decisions/0014-multi-app-package-boundaries.md).

## Display names

`profiles.display_name` is the canonical display name. It is optional and set by the person; at an OAuth sign-up the signup trigger prefills it once from the provider's `full_name`, else `name`. It is never derived from `first_name` or `last_name`. Saving a display name mirrors it into `user_metadata.full_name`, which is what the header reads from the token. `displayNameOf` resolves what to show; forms edit the raw value.

## Structure

Capability files under `src/`, each with its tests beside it (workspace conventions, domain packages): `credentials`, `names` (display, first and last name rules, `checkName`, `initialsOf`, `displayNameOf`), `avatar`, `profile`, `current-user` (types), `oauth-providers`, `identity-result` (types) and `profile-setup`. Dependencies run one way: `credentials` and `profile` use `names`; `profile` uses `avatar`.

## Rules

- A `VerifiedIdentity` comes only from a provider's verification of the session (see `@synapcity/server-auth`). Never build one from display data or from an ID a caller supplied.
- Development fixture identities are never represented here; fixture mode stays in the host app (ADR-0006, development amendment).
- Fields are added when a real consumer needs them.
- Name and avatar are display data. They are never used to authorize anything.
- The limits above mirror external systems (database check, storage bucket). If one changes, change the other.

## Scripts

`lint`, `check-types`, `test`, `test:coverage`. Tests sit beside each capability (`*.test.ts`); `index.test.ts` pins the root entry's exports. The identity types are exercised by their consumers' type checks.
