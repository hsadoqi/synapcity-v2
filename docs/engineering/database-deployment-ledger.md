# Database deployment ledger

**Status:** Current direction. The operator's record of what is applied where, with the evidence for each claim.

This ledger is the only source of the project ref that the parity script (`pnpm db:parity`, `scripts/db-parity.mjs`) will accept as the expected one. A ref typed on its command line is refused. Rows in the Environments table are entered by the owner and reviewed in a pull request; an agent does not enter a ref.

A claim about hosted state belongs here only with its evidence (a date and where it came from). A row without evidence is not a fact. Migrations are immutable once merged to `main` (owner decision D3), and their headers saying "NOT applied by repository tooling" are not edited; this ledger is what states what is applied.

### Incident and release record: T1 (2026-11-02)

- **Uncontrolled application.** Production held all six T1 migrations, present by 2026-10-30 15:13:44 UTC, before the release procedure ran. The route and operator are unknown: the Supabase GitHub integration had production deployment off, and Postgres logs on this plan do not record statements. The three registered repository worktrees linked to Production were unlinked on 2026-11-02; five unregistered local copies stay linked as a follow-up. Write-capable access is under separate review.
- **What ran.** For `20261029100000` the applied statements equal `main`. The five `20261030…` versions equal the delivery-branch files before PR #138 (no `lock_timeout` line; one header comment). Their stored statements remain historical evidence; no migration or history row was edited.
- **Grant drift and repair.** `authenticated` lacked EXECUTE on `public.delete_own_account()`; no repository migration, test or script revokes it. PR #139 (merged as `755a2a9c`) added the forward-only `20261102064038_restore_delete_own_account_execute`, applied alone to Production after a recovery export; the post-repair catalog equals merged `main`.
- **Recovery (G1, G5).** R2, verified before and after the repair: encrypted logical exports, restore rehearsals into disposable local targets, the `avatars` Storage objects captured with a checksum manifest, and an off-device copy verified to mount. No platform backup or PITR is claimed. RPO is the changes since the last export; RTO is a manual restore into a replacement project (rehearsed at about 50 seconds for the current size).
- **Gates.** G1 PASS, G2 PASS, G3 PASS after the repair, G4 PASS, G5 PASS, **G7 FAIL** (SQLSTATE `57014`, zero measured samples; the scratch project was deleted afterwards).
- **Risk acceptance (owner, 2026-11-02).** G7 remains a failure. The release proceeds for the controlled development baseline only (Production holds 2 users, 2 Dashboards, 2 revisions). Synchronous account deletion works for small accounts and is not supported for heavy ones. Durable deferred account deletion — immediate access and session revocation, a durable deletion request, bounded, retryable and idempotent background cleanup, eventual Auth-user deletion, observable failures, and a new hosted scale validation — must be complete before broad public onboarding, paid-plan enforcement, an account-level storage or revision commitment, evidence of substantial account growth, or any claim of heavy-account deletion support. The unchanged V-8 benchmark is not rerun and its fixture and threshold are not weakened.
- **Follow-ups (non-blocking).** The V-8 runner omits the sanitized SQL error from its report, and its leftover-account check is case-sensitive while Auth stores emails lowercase.

## What a release adds

Each release train (database release 1, then 2, 3, 4) adds, after the procedure in [database-release.md](database-release.md) has run:

- the apply: date, operator, the migrations (versions), the target ref as checked against the Environments table;
- the post-migration check: the parity script's output, counts, the advisor results;
- the application deploy: the deployment id;
- the production smoke result;
- each risk acceptance the train needs (unbounded per-account growth, with the monitoring queries scheduled).
