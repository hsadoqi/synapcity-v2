**Five highest-value consolidation opportunities**

1. **Calendar-date values** (D3). `yyyy-MM-dd` local parsing/formatting exists three times (`domain-time` values, `frontend-ui/lib/calendar-utils`, `domain-prototypes/utils/calendar`). `domain-time` is the right owner and is mid-extraction; finishing it removes a timezone-sensitive rule from two other places.
2. **Date/time display through the regional preference** (D4). `domain-preferences` already has `formatTime`, `calendarDaysBetween` and `formatRelativeDay`, and the date picker, calendar and document details use them. Dashboard agenda times and every collection date re-implement them with the browser locale or hard-coded `en-US`, so a person's clock and locale choice is honoured on some screens and not others.
3. **Loading announcement contract** (D11). Five loading surfaces announce themselves four different ways; one (`DashboardWorkspaceSkeleton`) puts its text outside any live region. `LoadingRegion` already encodes the right contract.
4. **Form feedback contract** (D7). `FormFeedback`, `FieldFeedbackState`, `ActionFormRefusal` and `FormMessageState` are four names for `{ error?, fields?, message? }` inside one package.
5. **Pin result contracts and the duplicate app Server Action** (D12). Two identical server outcomes, two identical browser results, and `setSpacePinned` / `setRecordPinnedFor` written twice in `apps/web`.

**Most important keep-separate conclusions** (section 5)

- `getCaller` and `getCallerIdentity` return different things for different actions; they only share a three-line message mapping.
- The settings draft model and the dashboard save scheduler are different persistence models (explicit save versus autosave) and must stay separate.
- `SettingRow`, `SettingsSelect` and `SettingsCombobox` are settings-semantic adapters over the same `frontend-ui` primitives that the form renderers adapt; merging them into the form engine would add modes, not remove code.
- Element-width observers differ in timing and hysteresis on purpose.
- Per-package `ResizeObserver`/`getAnimations` polyfills are a documented decision in `dev-vitest-config`.

**Does the architecture encourage duplication?** Partly. ADR-0014 makes intra-`frontend` imports conditional but gives no ordering between `ui`, `blocks`, `forms`, `shells` and `collection`, and `frontend-blocks` has no README or ownership statement. The result is visible: `SearchForm` has moved shells → forms → blocks in a week, `forms` depends on `blocks` for three single controls (`PasswordInput`, `SearchInput`, `EntityDialog`), and `blocks` carries a complete second app shell. Where an owner _is_ written down (`frontend-preferences`, `features-settings`, `domain-time`), duplication is low. The highest-leverage fix is not a shared-components rewrite; it is a one-paragraph ownership statement for `frontend-blocks` and an explicit order among the frontend packages.

## 4. Detailed findings (P1–P2)

### D1 — `EntityFormDialog` rename left a broken consumer (P1)

**Duplicated behaviour.** None any more: `3f9aa94d` renamed `EntityFormDialog` to `FormDialog` (`packages/frontend/forms/src/components/form-parts/form-dialog/index.ts`) and removed the old export. This is the failure mode of a parallel public API that was removed before its consumers moved.

**Evidence.** `packages/features/dashboards/src/frontend/widgets/agenda-body/agenda-event-dialog.tsx:4` still imports `EntityFormDialog`; `origin/main` still exports it (`packages/frontend/forms/src/components/entity-form-dialog`), so the break was introduced on this branch. `packages/frontend/forms/README.md:28` still documents it.

**Verified impact.** `tsc` fails in `features-dashboards`, `web` (TS2305 and three TS7031 knock-on errors). Six dashboards tests fail with "Element type is invalid … got: undefined": the agenda widget's **Add event** dialog throws when opened. This is a user-facing break, not a type nit.

**Ownership.** `features-dashboards` owns the consumer; `frontend-forms` owns the README.

**Recommendation.** Migrate the consumer now. Do not add an `EntityFormDialog` alias unless the owner wants a deprecation window (D-reg 2); there is only one consumer.

**Migration outline.** Change the import and JSX to `FormDialog`; confirm `onSubmit` values are typed from the definition again; update the forms README row.

**Tests before/after.** `agenda-event-dialog.test.tsx` (4 failing) and `connected-widget.test.tsx` agenda cases (2 failing) must pass; `pnpm --filter @synapcity/features-dashboards check-types` and `web` check-types.

### D2 — A second app shell lives in `frontend-blocks` (P2)

**Duplicated behaviour.** `WorkbenchShell` (`packages/frontend/blocks/src/workbench-shell.tsx`) composes its own `SidebarProvider` (`:58`), header, workspace switcher (`main-header/workspace-dropdown.tsx`), sidebar navs (`main-sidebar/{project,resource,workspace}-nav.tsx`), icon rail (`sidebar-rail/sidebar-icon-rail.tsx`) and account menu (`main-sidebar/{user-avatar,dropdown-actions}.tsx`). Each has a production counterpart in `frontend-shells` (`RootShell`, `SidebarShell`, `ContextSwitcher`, `RootSidebar`) or `frontend-blocks` itself (`UserMenu`).

**Evidence of drift and leakage.**

- `packages/frontend/blocks/src/index.ts:10` exports `./data`, which holds demo workspaces with third-party image URLs (`data.tsx`), from the package's only public entry. ADR-0014 §2 allows fixtures only for dedicated tests, stories and demo hosts.
- `packages/frontend/blocks/src/index.ts:1-4` and `:17-20` export the same modules twice.
- `sidebar-rail/sidebar-icon-rail.tsx` and `blocks/user-menu/user-menu.tsx` import `next/link` from a framework-neutral entry (boundaries R11, two violations); `blocks/package.json` lists `next` as a runtime dependency.
- Boundaries also reports a module cycle (`dropdown-actions.tsx` ↔ `user-avatar.tsx`, R9) and 11 folder-index bypasses (R7) in this prototype.
- `apps/web/src/app/(protected)/playground/layout.tsx` mounts it inside the protected `AppShell`, so `/playground` renders two sidebar providers, an `h-svh` box inside a contained shell, and logs `source` on every request (`:13`). In HEAD, Cmd+B toggled both sidebars because each provider listened to the window; the concurrent working-tree change removes the provider's listener, so in the final state the workbench sidebar has no shortcut at all. Both providers still write the same `sidebar_state` cookie, which nothing reads.

**Real duplicate or adapter?** A real parallel implementation of the shell, not an adapter. Its prop surface (`Workspace`, `WorkspaceResource`) is a third workspace shape alongside Spaces and `RootBreadcrumb` contexts.

**Owner.** `frontend-shells` (ADR-0014 table: one `frontend/shells` package holds composable app shells).

**Recommendation.** Defer pending an owner decision (D-reg 3): is the workbench an experiment, a design reference, or the next shell? Until decided, the low-risk move is quarantine: take `./data` and the workbench exports out of the public barrel (stories can import by relative path) and remove the `console.log`. Per the preservation policy, archive rather than delete.

**Migration outline (if it becomes product).** Port the ideas into `frontend-shells` as `RootShell` slots (rail, resource selection), replacing `Workspace` with the Space contract; delete the duplicate navs only after `RootSidebar` covers them.

**Tests before consolidation.** `workbench-shell.stories.tsx` is the only coverage; it has no unit test. A shell port needs the existing `sidebar-shell.test.tsx` and `shell-containment.e2e.ts` to stay green.

### D3 — Calendar-date value helpers exist three times (P2)

**Evidence.**

- `packages/domain/time/src/values/date-value/date-value.ts:1-31` (untracked, new): regex `^(\d{4})-(\d{2})-(\d{2})$`, local `new Date(y, m-1, d)`, roll-over rejection, returns `undefined`.
- `packages/frontend/ui/src/lib/calendar-utils.ts:16-55`: the same regex, construction and roll-over check, returns `null`; adds `addCalendarDays`, `formatCalendarDate` (defaults to `en-US`) and `formatCalendarDay`.
- `packages/domain/prototypes/src/utils/calendar/calendar.ts:4-11`: `DAY_KEY_PATTERN` and a third local-parts formatter.
- `domain-time` also exports `calendarDateSchema` and `CalendarDate`, so the validation rule now has a schema form too.

**Real duplicate.** Yes: identical semantics, identical edge-case handling, different return sentinels.

**Owner.** `domain-time` (ADR-0014: frontend may import domain pure rules). `frontend-ui` already depends on `domain-preferences`, which depends on `domain-time`.

**Implications.** These rules exist to stop a calendar day moving across time zones; three copies is three places a future fix has to land. The `null`/`undefined` difference matters to callers that use `??` vs `!== null`.

**Recommendation.** Share the lower primitive. Migrate `calendar-utils` to call `domain-time` (keeping its `null` return as an adapter, or changing callers deliberately), then the prototypes helpers.

**Tests.** `calendar-utils.test.ts`, the new `date-value.test.ts`, and the downstream date-picker, agenda-date and time-picker tests. The blocks tests for agenda-date are currently not running (section 7), so fix that first.

### D4 — Date and time display bypasses the regional preference (P2)

**Evidence.** `domain-preferences/src/utils/date-time/date-time.ts` exports `formatTime` (`:62`), `calendarDaysBetween` (`:146`) and `formatRelativeDay` (`:160`), and `frontend-preferences` exposes `useDateTimeFormatting`. These are used by `apps/web/src/features/documents/components/document-view/document-details.tsx:29`, `frontend-ui` `date-picker.tsx:27` and `calendar.tsx:40`, and the settings preview.

Parallel implementations:

- `packages/features/dashboards/src/frontend/utils/time-format/time-format.ts:2`: `new Intl.DateTimeFormat(undefined, { hour, minute })` for agenda and calendar widgets (the staged change correctly merged two identical copies into this one).
- `packages/frontend/collection/src/utils/format-entity-date/format-entity-date.ts:13-25`: its own calendar-day difference and English "Today"/"Yesterday"/"N days ago", then `en-US`.
- `packages/frontend/collection/src/components/entity-date/entity-date.tsx:47`: `en-US` with `timeZone: 'UTC'` for the server render.
- `packages/frontend/collection/src/utils/collection-query/collection-query.ts:68`: `en-US` parts.

**Behaviour.** A person who sets a 24-hour clock or a non-US locale sees it in document details and the date picker but not in agenda times or collection dates.

**Owner.** Rules: `domain-preferences`. Hook: `frontend-preferences`. `frontend-collection` may import both (frontend → domain, frontend → frontend).

**SSR implication.** `EntityDate` deliberately renders a UTC label on the server and swaps on hydration; a preference-aware version must keep that or use the server-supplied regional settings that `RegionalProvider` already carries.

**Recommendation.** Defer pending a product decision (D-reg 4), then migrate consumers to the existing formatters. No new abstraction is needed.

**Tests.** `format-entity-date` tests, `entity-date` tests, agenda/calendar body tests with a non-default `DateTimeFormatting`, and a hydration test for `EntityDate`.

### D5 — Two owners for focus when a panel destination opens (P2)

**Evidence.** The contextual panel moves focus to its `tabIndex={-1}` region once the destination shows (`packages/frontend/shells/src/components/contextual-panel/contextual-panel.tsx:201-206`). The dashboards widgets destination calls `focusPalette()` (`dashboard-widgets-destination.tsx:36`), which polls every animation frame for up to 400 ms, and for 150 ms after landing takes focus back from `<body>` or a non-interactive `tabindex="-1"` container (`packages/features/dashboards/src/frontend/utils/focus/focus.ts:16-90`). `isStolen` exists to beat the panel.

**Real duplicate?** A duplicated state machine with conflicting ownership: both decide where focus lands on open, and correctness depends on timing (`GLIDE_MS = 200`, the settle window, Base UI's inert handling). It is intentional and covered by tests (PR #120; a `test/global-panel-glide-race` investigation worktree exists), so it is not an active bug.

**Owner.** `frontend-shells` owns the panel, so it should own the focus decision and let a destination name its first target.

**Recommendation.** Introduce a common contract only: for example a destination-level `initialFocus` (element, ref or selector) that the panel focuses instead of its region. Then delete the polling. Owner decision on the API shape (D-reg 5).

**Tests.** Contextual-panel and global-panel tests for focus-on-open with and without a destination target; the dashboards focus tests; `apps/web/e2e/global-panel.e2e.ts`. Browser behaviour is only partly covered by jsdom (no layout, no transitions), so the e2e and a manual keyboard pass are required.
