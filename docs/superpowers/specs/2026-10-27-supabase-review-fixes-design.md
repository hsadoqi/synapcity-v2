## 1. Review summary

The database layer needs no change. Every table enables RLS with an ownership predicate, grants are explicit and column-level, every `UPDATE` policy has `USING` and `WITH CHECK`, policies use `(select auth.uid())`, owner columns are indexed, and both `SECURITY DEFINER` functions set `search_path = ''` and restrict `EXECUTE`. Supabase's change that stops exposing new `public` tables to the Data API automatically (changelog, enforced on all projects from 2026-10-30) does not affect this project, because every migration grants explicitly.

The TypeScript layer works but has one confirmed behaviour bug (A1), one likely one (A2), code in the wrong home, and repeated code. Findings as corrected in section 7; the Disposition column gives the outcome:

## 3. Design

### 3.1 Shared failure shape and helpers (B4, B5, C1, C2, A4)

- One `ProviderFailure` in `server-auth` (it is already exported there). `server-supabase` re-exports the type for its callers and deletes its own definition; `server-account` replaces `AccountPreferencesFailure` with it, and `features-settings`' `loadSettingsAccountPreferences` takes it.
- `server-supabase/src/provider-failure/`: `toProviderFailure(error)` takes any `{ code?, status? }` and returns `{ code?, status? }` with absent keys left out, matching the identity provider's `detail`. It replaces the six hand-written conversions. It is exported, because `server-account` needs it. `readProviderUser`'s failures stop carrying keys set to `undefined`; no caller reads the difference.
- `server-supabase/src/auth-errors/`, internal: `classifyAuthError(error)` returns `signed-out`, `unavailable` or `{ kind: 'provider-error', code }` using `isAuthSessionMissingError` and `isAuthRetryableFetchError`. The leftovers spec (4.8) rejected wrapping `isAuthRetryableFetchError` alone; this helper replaces a three-way mapping, not a one-line predicate. _Superseded: "and `rateLimited(error)` returns the rate-limit outcome or null". By the same 4.8 reasoning, a wrapper over the two-line `isRateLimited` check is not worth a module; the operations keep calling `isRateLimited`._
- `changeEmail`, `resendEmailChange` and `sendOwnPasswordReset` read the user through `readProviderUser` (C2; leftovers F1). Their outcomes do not change: today any non-network error is already `signed-out`.
- `caller.ts`, `save-name.ts`, `save-avatar.ts` and `settings/server/account-preferences.ts` use `SupabaseServerClient`; the `Supabase` alias is deleted (B5). `owned-records.ts` is deleted by section 3.4 instead.
- `readAccountPreferenceRow` and `writeAccountPreferenceRow` return `toProviderFailure(error)` (A4). `schema_version: 1` stays, with a comment pointing at the preferences schema version it mirrors.

### 3.2 Remaining auth operations (B1, A1, C7)

New operations in `auth-operations`, each taking the request client first and returning a small outcome, as the other seven do:

| Operation                                 | Replaces inline call in     | Outcome                                                                                                      |
| ----------------------------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `signInWithPassword(client, input)`       | `signInWithPassword` action | `signed-in` with `userId`, or `refused` with `code` (the action keeps its message mapping and `unconfirmed`) |
| `resendSignupConfirmation(client, input)` | `resendConfirmation` action | `accepted`, or `rate-limited` with `code`; every other result is `accepted`, as today                        |
| `updateOwnPassword(client, input)`        | `updatePassword` action     | `updated` with `userId`, or `provider-error` with the failure                                                |
| `startOAuthSignIn(client, input)`         | `signInWithOAuth` action    | `redirect` with `url`, or `provider-error`                                                                   |
| `signOutSession(client, { scope })`       | `signOut` action            | `signed-out`, or `failed` with the failure and `thrown: true` when the SDK threw; never throws               |
| `exchangeAuthCode(client, code)`          | `/auth/callback` route      | `signed-in` with the user fields the arrival rules read, or `failed`                                         |

The actions and the route keep FormData and query parsing, messages, revalidation and redirects; the route stays a host entry, as the ownership map requires. `signOut` passes the scope chosen in R1.

C7: `logFailure(operation, failure, detail?)` gains an optional third argument of string or boolean fields that are safe to log (`provider`, `thrown`). The eight hand-written `console.warn` calls in `actions.ts` use it, with the same operation names and fields as today.

### 3.8 Email links (A2)

Only after Task 1 reproduces the failure and R2 is approved:

- New route `apps/web/src/app/auth/confirm/route.ts`: reads `token_hash`, `type`, `next` and `flow`; calls `verifyOtp({ type, token_hash })` through a new `server-supabase` operation `verifyEmailLink(client, input)`; then follows the same arrival rules as `/auth/callback` (welcome step, notices, safe `next`, the secure-email-change first step). The arrival rules move into one shared function used by both routes.
- How `next` and `flow` arrive: the actions pass `emailRedirectTo` as `/auth/confirm?next=…&flow=…` instead of `/auth/callback?…`, and each template links to `{{ .RedirectTo }}&token_hash={{ .TokenHash }}&type=…`. `{{ .RedirectTo }}` is a full URL, so it is never put inside `next`. `/auth/confirm` is added to the redirect allow-list locally and in the hosted project. Task 1 confirms that `{{ .RedirectTo }}` keeps its query string.

## 9. Pre-commit investigation, 2026-10-27

### 9.1 Why a fresh database stops at `20261013184213`

Read-only queries against the hosted project (`supabase db query --linked`, catalogue `SELECT`s only) show:

- Its migration history holds exactly the 11 repository migrations. None creates `public.rls_auto_enable()`.
- The function is owned by `postgres`, belongs to no extension, is `SECURITY DEFINER` with `search_path` `pg_catalog`, and runs from the `ensure_rls` event trigger (`ddl_command_end`, `CREATE TABLE`, `CREATE TABLE AS`, `SELECT INTO`), also owned by `postgres`. Every Supabase platform event trigger (`issue_pg_*`, `pgrst_*`) is owned by `supabase_admin`. The body is the Row Level Security guide's example.
- Postgres is 17.11; `config.toml` said 15.

So the function is not platform bootstrap, not an extension and not missing history of ours: it was added to the hosted project outside migrations, and `20261013184213` (which revokes `EXECUTE` on it) assumes it. That is schema drift in a non-application object, and the reason the history cannot build a fresh database. How it was added (the dashboard or the SQL editor) is not recorded.

### 9.2 Decision: how fresh databases get the function

**Owner decision, 2026-10-27:** (a). `supabase/migrations/20261013184200_declare_rls_auto_enable.sql` is the tested draft below, with one added comment paragraph. The hosted project needs `supabase db push --include-all` once, run by the owner after merge.

The applied migration stays as it is in every option.

| Option                                                                                                                                                        | Fresh install (local, CI, preview branch, new project)          | Hosted project                                                                                                                    | History                                                                                                  |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| (a) **Recommended.** A guarded migration, `20261013184200_declare_rls_auto_enable.sql`, before the revoke: creates the function and trigger only where absent | Works everywhere                                                | Applied once with `supabase db push --include-all`; changes nothing (tested: body, grants and trigger identical before and after) | Append-only in content; one out-of-order version, which the CLI refuses unless `--include-all` is passed |
| (b) `supabase/roles.sql`, which `supabase start` runs before migrations                                                                                       | Local and CI only; preview branches and new projects still stop | Untouched (unless someone runs `db push --include-roles`)                                                                         | Unchanged, but the dependency stays undeclared, in a file meant for roles                                |
| (c) A migration after the revoke                                                                                                                              | Does not help: the revoke fails first                           | Declares the function going forward                                                                                               | Unchanged                                                                                                |

(a) is the only option under which the migrations alone build a working database everywhere, and it records the hosted state instead of leaving it as drift. Tested on a throwaway Postgres 16 with the CLI's own runner (`migration up --db-url`): a fresh install applies all 12 migrations and produces a function definition identical to the hosted one; a hosted-shaped database (function, trigger and grants present, 11 migrations recorded) is refused without `--include-all` and unchanged with it. It also turns on automatic RLS for new `public` tables in local and CI databases, as on the hosted project; every table already enables RLS itself.

The draft as tested (the committed file adds one comment paragraph):

```sql
-- Declares public.rls_auto_enable() and its ensure_rls event trigger in the
-- migration history. The hosted project gained both outside migrations
-- (checked 2026-10-27: owned by postgres, not part of an extension, created by
-- none of the migrations, the body of the Row Level Security guide's
-- example), and the next migration, 20261013184213, revokes EXECUTE on the
-- function. Without this file a fresh database stops at that revoke.
--
-- Guarded: where the function or the trigger already exists (the hosted
-- project), this changes nothing, so the function's grants and body stay as
-- they are. Timestamped before 20261013184213 so a fresh database creates the
-- function first; on the hosted project it is applied once with
-- `supabase db push --include-all` and does nothing there.

do $do$
begin
  if to_regprocedure('public.rls_auto_enable()') is null then
    create function public.rls_auto_enable()
      returns event_trigger
      language plpgsql
      security definer
      set search_path to 'pg_catalog'
    as $fn$
DECLARE
  cmd record;
  tbl name;
BEGIN
  FOR cmd IN
    SELECT *
    FROM pg_event_trigger_ddl_commands()
    WHERE command_tag IN ('CREATE TABLE', 'CREATE TABLE AS', 'SELECT INTO')
      AND object_type IN ('table','partitioned table')
  LOOP
     IF cmd.schema_name IS NOT NULL AND cmd.schema_name IN ('public') AND cmd.schema_name NOT IN ('pg_catalog','information_schema') AND cmd.schema_name NOT LIKE 'pg_toast%' AND cmd.schema_name NOT LIKE 'pg_temp%' THEN
      BEGIN
        SELECT c.relname INTO tbl FROM pg_catalog.pg_class c WHERE c.oid = cmd.objid;
        EXECUTE format('alter table if exists %I.%I enable row level security', cmd.schema_name, tbl);
        RAISE LOG 'rls_auto_enable: enabled RLS on %', cmd.object_identity;
      EXCEPTION
        WHEN OTHERS THEN
          RAISE LOG 'rls_auto_enable: failed to enable RLS on %', cmd.object_identity;
      END;
     ELSE
        RAISE LOG 'rls_auto_enable: skip % (either system schema or not in enforced list: %.)', cmd.object_identity, cmd.schema_name;
     END IF;
  END LOOP;
END;
$fn$;
  end if;

  if not exists (select 1 from pg_catalog.pg_event_trigger where evtname = 'ensure_rls') then
    create event trigger ensure_rls
      on ddl_command_end
      when tag in ('CREATE TABLE', 'CREATE TABLE AS', 'SELECT INTO')
      execute function public.rls_auto_enable();
  end if;
end
$do$;
```
