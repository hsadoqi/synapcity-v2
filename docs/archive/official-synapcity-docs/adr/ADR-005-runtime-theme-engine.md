# ADR-005: Use a Runtime Palette Theme Engine

## Status

Accepted for current theming direction.

---

## Context

Synapcity needs user-customizable themes at multiple scopes: root, dashboard, document, panel, and widget.

Compile-time theme variants are not flexible enough for arbitrary user colors and scoped overrides.

---

## Decision

Use a runtime palette theme engine that stores canonical OKLCH seed values, generates primary/accent palette scale variables, and writes those variables to explicit theme scope roots.

Semantic variables are not generated by the runtime engine. They are mapped in `globals.css` from generated palette variables.

---

## Rationale

- Supports arbitrary user colors.
- Supports scoped inheritance through CSS cascade.
- Avoids Tailwind rebuilds.
- Keeps components semantic-token driven.
- Allows instant preview.
- Preserves a neutral product identity while allowing personalization.

---

## Tradeoffs

Runtime generation requires careful performance and hydration handling.

Generated colors must be accessibility-checked against the semantic mappings in `globals.css`.

---

## Consequences

- Components use semantic tokens only.
- Store design inputs, not generated CSS.
- Store `ThemeRecord` separately from scope assignments.
- `data-theme-id` refers to the persisted theme record id.
- Theme provider owns scope resolution and palette variable application.
- Inherited scopes skip generation and inherit variables from parents.
- Theme editor must explain inherited vs explicitly themed values.
