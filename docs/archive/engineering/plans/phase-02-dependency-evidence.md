## Conflicts and resolutions

### Conflict 1 — `@storybook/addon-vitest` peer range excludes the repository's accepted Vitest version (RESOLVED)

- Repository's accepted, installed version: Vitest `^5.0.2` (ADR-0004, Phase 1 baseline).
- `@storybook/addon-vitest@10.6.0` (the version matching the plan's proposed Storybook 10.6.x generation) declares `peerDependencies.vitest: "^3.0.0 || ^4.0.0"` — this excludes Vitest 5.x entirely. Verified directly against the npm registry, not inferred.
- No Vitest-5-compatible release of this addon exists at time of writing; the next version line (`11.0.0-alpha.*`) is alpha and not appropriate to adopt for this reason alone.
- **Resolution (confirmed by the repository owner):** `apps/storybook` installs an isolated `vitest ^4.1.11` in its own `package.json`, separate from the root/every-other-workspace Vitest `^5.0.2`. This is not a workaround — [Storybook's first-party Vitest addon docs](https://storybook.js.org/docs/writing-tests/integrations/vitest-addon) explicitly recommend a separate [test project](https://vitest.dev/guide/projects) or [workspace file](https://v3.vitest.dev/config/#workspace) for isolating the addon's Vitest config from a monorepo's other Vitest setup. [Vitest's migration guide](https://vitest.dev/guide/migration.html) confirms `test.projects` syntax itself is unchanged between v4 and v5 (only the default inheritance behavior changed), so nothing about the addon's behavior is compromised by running on 4.1.11. Recorded in [ADR-0012](../../architecture/decisions/0012-storybook-surface.md).
- This does not amend ADR-0004: the root and every other package/app remain on Vitest `^5.0.2`, unchanged.
- Consequence: `apps/storybook`'s browser tests run through their own local Vitest 4.x process (e.g. a `test:storybook` task), separate from the root's `test.projects` array — consistent with the design's own proposal (§9.2) that `pnpm test:storybook` was already a separate command from `pnpm test`.

### Correction — Base UI package was renamed and reached GA (found during P2-03)

- Originally recorded here as `@base-ui-components/react@1.0.0-rc.0`, checked against `peerDependencies`/`engines` only. That package is npm-deprecated: `npm view @base-ui-components/react deprecated` returns _"Package was renamed to `@base-ui/react`"_ (same repository, `mui/base-ui`). The renamed package has since reached GA and is currently `1.8.0`.
- This was missed in the original Slice 1 evidence pass because the `deprecated` registry field wasn't explicitly checked — only `engines`/`peerDependencies` were, despite `AGENTS.md` §7a requiring deprecation claims to be evidenced too. A full re-check of every other Phase 2 dependency's `deprecated` field (done during P2-03) found no other instances.
- Not a hard blocker — the fix is strictly a currentness correction (deprecated pre-GA package → current GA successor under the same maintainers), recorded as an amendment in [ADR-0011](../../architecture/decisions/0011-ui-and-styling-foundation.md).

## Historical contract note — P2-01 (#23)

**This section documents a historical contract violation. It does not reclassify P2-01 as
passing.**

P2-01's evidence-gathering slice explicitly prohibited any `package.json`, `pnpm-lock.yaml`, or
`pnpm-workspace.yaml` change — see this document's own header above ("No `package.json`,
`pnpm-lock.yaml`, or `pnpm-workspace.yaml` change accompanies this document"). That constraint was
violated: commit `062c3bf` ("docs: add phase 2 dependency evidence and technical decision ADRs
(#31)") modified the root `package.json`, changing the `deps:boundaries` script from
`depcruise packages --config .dependency-cruiser.cjs` to
`depcruise packages $( [ -d apps ] && echo apps ) --config .dependency-cruiser.cjs`.

Verified facts about this violation (checked directly against the commit, 2026-09-28):

- `git show 062c3bf -- package.json` shows the one-line script change above landed in the same
  commit as this evidence document's introduction.
- `git show --stat 062c3bf -- pnpm-lock.yaml pnpm-workspace.yaml` shows **no** change to either
  file in that commit. This proves no dependency addition or lockfile/workspace-manifest change was
  _committed_ as part of this violation. It does not prove that no install command ever ran during
  the slice — a frozen install (`pnpm install --frozen-lockfile`) is a routine CI/local operation that
  does not touch the lockfile, so Git history cannot rule that out. The defensible claim is limited to
  what Git can actually show: no dependency addition or lockfile/workspace-manifest change was
  committed as part of this violation.
- The change was mechanical (extending an existing script to also cover `apps/` once that
  directory existed) and not a disguised dependency addition, but it was still a manifest change
  made during a slice whose own stated scope explicitly excluded manifest changes.

This is recorded as a historical contract violation, not retroactively excused, and not treated as
evidence that P2-01's original acceptance criterion ("no manifest changes in this slice") passed.
No repository convention for an explicit owner waiver of a historical CI/process violation was
found in this repository (no waiver log, exception register, or equivalent mechanism exists as of
2026-09-28), so none is claimed here. If the repository owner wants to formally accept this as a
one-time exception, that decision and its rationale belong in a note added by the owner, not
fabricated here.

### Owner acceptance — 2026-09-28

I accept the documented P2-01 historical contract violation as a bounded Phase 2 exception. The
violation consisted of a root `package.json` script change during a slice that prohibited manifest
changes; no dependency addition or lockfile/workspace-manifest change was committed as part of that
change. This does not retroactively satisfy the original acceptance criterion. The exception is
accepted for Phase 2 closeout because the discrepancy is documented, bounded, and does not undermine
the current technical foundation.

Classification: `ACCEPTED HISTORICAL EXCEPTION`. P2-01's original acceptance criterion remains
failed, not `VERIFIED`. The same decision is recorded in
`docs/engineering/verification/phase-02-verification-record.md` (Round 3).
