# Product principles

**Status:** Canonical product principles

## 1. Useful before configurable

Synapcity provides coherent product-defined defaults before asking the user to personalize them. Configuration improves fit; it is not a prerequisite for value.

## 2. Product-defined capability, user-composed context

Synapcity defines meaningful capabilities, constraints, and interaction semantics. Users compose those capabilities for their own contexts without becoming responsible for designing the domain model.

## 3. Context, not mandatory containment

A user-defined contextual environment helps organize and specialize work. It does not existentially own everything presented within it.

## 4. Creation context establishes defaults, not permanent ownership

Creating information within a context may preselect useful presentation, organization, or configuration. It does not permanently bind the information to that context.

## 5. Context can modify experience without modifying identity

Navigation, presentation, customization, capability emphasis, and continuity may vary by context while the canonical thing retains its identity.

## 6. Context and surface are independent dimensions

Changing a Document or Dashboard does not necessarily leave the current context. Entering another context does not necessarily create another copy of the current information.

## 7. Generic interoperability, specialized behavior

Capabilities participate in shared identity, context, discovery, reference, and history where useful without being collapsed into one generic record model.

## 8. Representations do not silently become second owners

A Dashboard, Widget, contextual surface, or live representation may own legitimate presentation configuration. It must not silently acquire a divergent copy of information owned elsewhere.

## 9. Reuse is intentional

Showing the same thing, referencing it, copying it, and detaching or forking it express different user intentions. Product behavior must preserve those distinctions.

## 10. Preserve working context

Inspecting related information, capturing a thought, or using a lightweight utility should not unnecessarily destroy the user's current working context.

## 11. Meaningful things are addressable where value requires it

Addressability exists to support navigation, connection, annotation, history, and resumption. It is granted deliberately; it is not a mandate to assign global identity to every implementation node.

## 12. Information can outlive its context without losing its history

Current organization may change while provenance and meaningful lineage remain available. The originating context must not become a permanent prison or be silently erased.

## 13. History describes meaningful change

User-visible history records committed, understandable events. It is not a raw stream of mouse movements, preview values, internal state transitions, or analytics events.

## 14. Progressive disclosure

Sophisticated infrastructure does not justify exposing equal complexity to every user. Advanced configuration and concepts appear when they become useful.

## 15. Bounded customization serves the work

Personalization supports contextual identity and user comfort within a coherent, accessible product. Customization is not the product's purpose.

## 16. Product claims are behaviorally honest

Affordances and copy that imply computation, persistence, recency, recovery, synchronization, or destructive effect correspond to real behavior. Prototypes and fixtures identify themselves.

## 17. Examples do not become domain types

Use cases explain intent. They do not automatically establish entities, enums, schemas, or capability taxonomies.

## 18. Uncertainty remains visible

An unresolved decision is part of the product record. It must not be hidden in a route, fixture, schema, package, default, or implementation convenience.
