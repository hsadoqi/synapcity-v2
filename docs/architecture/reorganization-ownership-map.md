# Reorganization ownership map

**Status:** Current direction, governed by [ADR-0014](decisions/0014-multi-app-package-boundaries.md).
**Snapshot:** `91be9693`, inspected on 2026-10-23 in the architecture-reorganization worktree.
**Scope:** Current source families, target responsibility owners, and preservation boundaries. This is an ownership reference, not a file-move manifest or a parallel milestone/status tracker.

## How to use this map

A row can split a current folder across several owners. Classify the actual module and its consumers before moving it; a folder name is not evidence of semantic ownership. Target groups below are responsibility families, not claims that manifests or exports already exist.

The category and grouping decisions are settled by ADR-0014. Exact filenames, package manifests, export names, host bindings, and migration artifact budgets are specified in Milestone 3 and the relevant execution scope. Existing working capability labels continue as internal migration handles; final product terminology remains governed by the glossary.

## Named transition cases

These are snapshot observations, not permanent allowances or completed remediation:

| Case                                           | Current source                                                | Target condition                                                                                    |
| ---------------------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Product contracts in UI                        | UI types (the Space schema moved in M5.1)                     | One domain owner; consumers use that contract                                                       |
| App-local capability implementation            | The nine web feature families                                 | Reusable responsibilities moved to their mapped owners; host binding stays in app                   |
| Framework-coupled presentation                 | Next.js imports in UI and collection                          | Explicit host/framework binding with a portable presentation interface                              |
| Fixture-backed production-path composition     | Home and Space detail data/composition                        | Clearly separated production/demo providers; no unlabelled synthetic records or fake-success claims |
| Divergent fixture models and repeated identity | Dev fixture factories and local resource fixtures             | Contract-aligned, deterministic factories/scenarios with per-record identity                        |
| Inconsistent `shared` meaning                  | Settings presentation/browser effects mixed with pure modules | Classify portable contracts, frontend effects, and feature presentation explicitly                  |
| Narrow boundary enforcement                    | Web direct-import test                                        | Workspace/runtime/public-interface protection implemented and violation-tested in Milestone 3       |

A migration task scope owns the exact source/target files, temporary bridges, affected consumers, verification, and removal conditions. Update observed locations after a completed move; do not mirror execution task status or create a second planning system in this map.

## Preservation and exit expectations

Preserve URLs, IDs, serialized shapes, auth/session and provider behavior, database access rules, preference precedence/storage keys, accessible interactions, and existing meaningful test/scenario coverage. Tests, stories, style scanning, and app wiring must follow each extraction.

A migration checkpoint demonstrates that its real consumer works through the public interface, temporary bridges have a bounded removal path, prohibited dependencies are detected, and the applicable repository gate is reported honestly. Existing prototype gaps are handled explicitly; no documentation row authorizes new external effects.

This map completes the ownership-assignment part of Milestone 2. Package manifests/exports and automated checks are Milestone 3; source movement and live-provider proof belong to subsequent implementation scopes. The Milestone 1 baseline (`pnpm verify` on `1390871e`) is recorded in the [task-scope ledger](../../.agents/task-scope.md).
